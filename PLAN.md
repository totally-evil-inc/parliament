# Document styling persistence to the client gate

## Context
- Audit how document customization (templates, presets, themes, block/layout styling) is modeled, stored, transformed, and rendered for proposals and invoices.
- Current symptom: documents rendered in the public client gate lose or omit the styling used during construction in the command/editor experience.
- Product decisions: freeze the exact presentation at send time; keep the gate as live responsive HTML driven by snapshot data; cover both new sends and existing public links; preserve all document presentation, not only palette.
- Intended outcome: a sent/public document is a self-contained, versioned presentation snapshot so the client gate is independent of later workspace/app theme changes or template implementation changes.

## Findings so far
- The canonical draft already has `template: { id, version, overrides }` in `packages/document/src/schema.ts`; it is stored inside the JSON document alongside `composition.blocks` and `assets`.
- `packages/document/src/presentation.ts` owns preset definitions (`classic-light`, `classic-dark`, `proposal-web-studio`), token options, and `getDocumentTemplate()`/`getDocumentTemplateStyle()`. The style is converted to CSS variables at render time rather than persisted as CSS.
- The command customization UI is in `packages/document-editor/src/components/document-block-sidebar.tsx`. Color, font, spacing, radius, and preset changes call the host route's `onTemplateChange`; proposal/invoice routes then write `id`, `version: 1`, and the full `nextTemplate.tokens` into the draft store via `setTemplate()`. This means explicit customization is usually persisted, but the route-local resolved default is not persisted when no customization action occurs.
- Header layout is not part of `template`; it is encoded as `partyHeader.config.layout`/TipTap `documentHeader.attrs.headerLayout` and needs to be included in the all-presentation audit. Block variants/configuration already live in `composition.blocks`.
- Draft persistence validates the full document (`safeParse*Draft`) and stores JSON in `proposal_draft.document`/`invoice_draft.document`; proposal saves also write `proposal_version.proposalDraft`, while invoice saves do not currently write an equivalent current version row.
- Both command server finalizers and the auth agent send path call `packages/document/src/finalize.ts`, which validates the full draft, hashes the document/render model, and writes the full `snapshotPayload.document` to `proposal_snapshot.document`/`invoice_snapshot.document`. Snapshot tables also duplicate only `templateId` and `templateVersion` as indexed metadata. The existing JSON snapshot is therefore the natural single persistence boundary; a new style table/column would duplicate data unless a future query requirement appears.
- Auth public endpoints read the snapshot JSON directly, parse it with the canonical schema, and return it unchanged through `@workspace/document/public-api`. The gate builds a render model from that document and both views call `getDocumentTemplate(model.template, appTheme)`, then apply `getDocumentTemplateStyle()` to CSS variables. This is the public rendering boundary that must stop consulting viewer/app theme for document styling. Proposal metadata also joins the mutable `proposal_draft.title` while the full document comes from the immutable snapshot; that should be aligned so the gate's challenge metadata is snapshot-consistent.
- Therefore, the current code path is conceptually capable of preserving styling when `template.overrides` is present in the snapshot. The concrete design flaw is that generic `proposal-classic`/`invoice-classic` references do not carry the resolved default tokens: the command editor resolves them from the authenticated user's `appTheme`, but the routes never materialize that effective template back into the draft before save/send. The gate then hardcodes `appTheme="light"`, so a document constructed under the dark app theme (or any future changed base preset) is rendered with a different baseline. A direct domain check confirms a fresh draft persists only `{id: "proposal-classic", version: 1}` while light/dark resolution produces different token sets. Custom preset/token edits generally do write full token overrides (the web-design blueprint round-trips its mint tokens through finalize), but this is not enforced at the send boundary. A second gap is that asset descriptors are persisted but the gate currently renders image/logo placeholders. Existing tests mostly use default templates and do not assert persisted custom tokens survive finalize → DB/public API → gate.
- There are two send implementations that must remain equivalent: `apps/command/src/server/{proposals,invoices}.ts` and `apps/auth/src/agent/document-send.ts`. There are also two public stacks: command server functions and the auth Hono API, though the gate uses the latter.
- The existing rendering CSS uses document variables for issuer-authored blocks, while acceptance/payment/status cards contain gate-owned semantic colors. The plan should preserve the former and intentionally leave the latter as client-gate chrome. Font tokens also resolve to ambient CSS/imported fonts in `packages/ui/src/styles/globals.css`; exact typography parity requires pinning the font mapping/version and verifying the same font resources are available in gate.

## Approach
- Make presentation a first-class, server-safe canonical contract rather than relying on template IDs resolving from the viewer's current app theme or mutable runtime definitions. Recommended first implementation: keep the existing document JSON as the single source of truth, but require a normalized persisted template reference whose `overrides` contains the complete validated resolved token set at save/finalize time. Preserve preset identity/version in `id`/`version`; do not add a parallel style table/column.
- Centralize normalization/expansion and snapshot construction in `@workspace/document` so command sends, agent sends, print rendering, auth APIs, and gate rendering cannot diverge. Add a pure `normalizeDocumentTemplateReference()`/resolved-template path: editor hydration materializes its effective theme into the draft before save/send, while finalization defensively normalizes legacy/incomplete refs with a deterministic fixed fallback.
- Freeze the resolved token values, header/layout presentation, block configuration/variants, and asset references at send time. The public API returns the snapshot document/presentation; the gate renders only that snapshot and does not use the viewer's app theme as a source of document styling.
- Add compatibility handling for legacy snapshots: prefer explicit snapshot presentation, derive from legacy document fields when complete, then use the existing template metadata/defaults only as a marked fallback; backfill existing links where the source document contains enough information and report/manual-review the remainder.
- Preserve live HTML/responsive behavior; this is not a PDF-first change. Keep acceptance/payment UI separate from the issuer-authored document presentation, with explicit tokens/variants for any gate chrome that is intentionally outside the document.

## Files to modify
- `packages/document/src/schema.ts`, `packages/document/src/presentation.ts`, `packages/document/src/finalize.ts`, `packages/document/src/render.ts`, `packages/document/src/public-api.ts`, and likely a new presentation normalization module plus tests.
- `packages/database/src/schema/proposal.ts`, `packages/database/src/schema/invoice.ts`, schema index/migrations, and shared database exports should be inspected for compatibility; the recommended token-normalization path expects no table migration, except an optional renderer/schema metadata migration.
- `apps/command/src/server/proposals.ts`, `apps/command/src/server/invoices.ts`, and the proposal/invoice editor routes where send-time data is assembled.
- `apps/auth/src/agent/document-send.ts`, `apps/auth/src/lib/public-document/{proposals,invoices}.ts`, `apps/auth/src/routes/public-document.ts`, and relevant API/send tests.
- `apps/gate/src/App.tsx`, `apps/gate/src/components/{ProposalView,InvoiceView,document-block-renderer,document-header-renderer}.tsx`, `apps/gate/src/lib/api.ts`, `apps/command/src/routes/documents/print.tsx`, `apps/command/src/features/documents/print/proposal-print-view.tsx`, and presentation tests.
- A one-off/idempotent legacy snapshot backfill task (likely under `apps/auth` or `packages/database`) and any asset-serving path remain to be confirmed.

## Reuse
- Reuse `parseProposalDraft`/`parseInvoiceDraft` and their strict Zod schemas as the input boundary.
- Reuse `getDocumentTemplate`, `getDocumentTemplateStyle`, token option definitions, and existing preset constants while moving their resolution into a deterministic snapshot-safe path.
- Reuse `finalizeProposalDraft`/`finalizeInvoiceDraft` as the single send-time boundary, including stable hashing and calculation-version metadata.
- Reuse `buildProposalRenderModel`/`buildInvoiceRenderModel` and the existing gate block renderers; make them consume the normalized resolved template without duplicating style logic.
- Reuse immutable `proposal_snapshot`/`invoice_snapshot` plus public-link foreign keys for freeze-at-send semantics; avoid introducing a second public-document lookup model unless the audit finds legacy data cannot be represented safely.
- Reuse existing public API discriminated-union schemas and gate query/mutation flow; the normalized document contract should remain compatible with current `document` responses and be validated at both server and client boundaries.

- Run a legacy-link matrix covering complete legacy documents, missing overrides, invalid/unknown template IDs, and backfilled snapshots.

## Resolved product decisions
- Freeze the presentation at send time; later workspace edits do not alter an existing public link.
- Apply the fix to both new sends and existing links, with compatibility/backfill behavior for legacy snapshots.
- Preserve all document presentation in scope: global tokens/presets, typography, spacing/radius, header layout, block variants/config, and relevant assets.
- Keep the client gate as responsive live HTML driven by snapshot data, rather than making PDF/rendered output the primary gate.
